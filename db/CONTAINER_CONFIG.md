# Container connection contract

How graph database code connects to the local container stack defined in
`deploy/container/`.

This document is the contract between the container plane and `db/`. The
container plane owns the server, network, credentials, and lifecycle. `db/`
owns the Graphiti client, ontology, and query behaviour.

## Endpoint

| Context                        | Host        | Port   | Auth                                   |
| ------------------------------ | ----------- | ------ | -------------------------------------- |
| Process inside the stack       | `falkordb`  | `6379` | password required                       |
| Process on the host, debug up  | `127.0.0.1` | `16379`| password required                       |
| Process on the host, base up   | —           | —      | no host port exists; host access fails  |

The service is `falkordb` in Compose project `sentinel-hunter-container`. Its
DNS name inside `sentinel-graph` is `falkordb`. The image is pinned to
`falkordb/falkordb-server:v4.22.4` (server only, no browser UI).

The password is `FALKORDB_PASSWORD` in `deploy/container/.env`. That file is
git-ignored and generated by `deploy/container/init-env.sh`. Read it rather
than hard-coding a value:

```sh
set -a
. deploy/container/.env
set +a
```

## Environment variables

`db/graph_client.py` reads exactly these names:

| Variable                | Value in the stack        | Notes                                         |
| ----------------------- | ------------------------- | --------------------------------------------- |
| `FALKORDB_HOST`         | `falkordb`                | `127.0.0.1` only for host-side debug access    |
| `FALKORDB_PORT`         | `6379`                    | `16379` only for host-side debug access        |
| `FALKORDB_PASSWORD`     | value from `.env`         | required; server rejects unauthenticated calls |
| `FALKORDB_DATABASE`     | `sentinel_lite`           | FalkorDB graph name used by the Graphiti driver|
| `GRAPHITI_GROUP_ID`     | `sentinel_lite_main`      | application-level namespace from `db/config.yaml` |
| `GRAPHITI_MAX_COROUTINES`| `4`                       | optional                                      |

`GRAPHITI_GROUP_ID` is not a connection setting; it scopes episodes and
searches. Keep it aligned with `db/config.yaml`.

## Known integration constraint: loopback guard

`db/graph_client.py` currently rejects any `FALKORDB_HOST` that is not
`127.0.0.1` or `localhost` (its protection against unauthenticated network
exposure). That guard blocks the in-container hostname `falkordb`, even though
`falkordb` is only resolvable on the internal `sentinel-graph` network and the
server requires a password.

Pick one of these, in order of preference:

1. **Relax the guard for the container hostname.** Accept `falkordb` as a
   second allowed host when the process is demonstrably inside
   `sentinel-graph` (for example, an explicit `GRAPH_CONTAINER_NETWORK=true`
   flag set only by the Compose service). This keeps host-side usage
   loopback-only while permitting the internal network.
2. **Run graph clients on the host against the debug overlay.** Start the
   stack with `./deploy/container/up.sh --debug up -d` and use
   `FALKORDB_HOST=127.0.0.1`, `FALKORDB_PORT=16379`. The published port is
   bound to loopback only. This satisfies the existing guard without changing
   `db/` code, at the cost of a host port and a debug-mode stack.
3. **Run the graph client inside a container attached to `sentinel-graph`.**
   It then uses `falkordb:6379`; this still requires the guard change from
   option 1 or a client that does not apply the guard.

Do not weaken the guard to accept arbitrary hosts. `sentinel-graph` being
`internal: true` is what prevents the graph from having internet egress; it is
not a substitute for the loopback-only rule on host-published ports.

## Persistence

- Volume: `sentinel-hunter-container_falkordb-data`.
- Mount point: `/var/lib/falkordb/data`.
- Durability: AOF enabled with `appendfsync everysec`; an RDB snapshot is also
  written at startup.
- Eviction: `--maxmemory 512mb --maxmemory-policy noeviction`. Writes fail when
  the graph is full instead of silently dropping nodes. Raise
  `FALKORDB_MAXMEMORY` and `FALKORDB_MEMORY_LIMIT` together in
  `deploy/container/.env`.
- `./deploy/container/up.sh down` keeps data.
- `./deploy/container/up.sh down -v` deletes the graph and is irreversible.

## Lifecycle

```sh
# One-time: generate credentials (refuses to overwrite an existing .env).
./deploy/container/init-env.sh

# Build and start; the orchestrator waits for a healthy FalkorDB.
COMPOSE_BAKE=false ./deploy/container/up.sh build
./deploy/container/up.sh up -d

# Verify auth, readiness, isolation, and TLS.
./deploy/container/verify.sh

# Host-side graph development against the same instance.
./deploy/container/up.sh --debug up -d
./deploy/container/verify.sh --debug
```

`verify.sh` fails if a base-stack service publishes a host port, if
`sentinel-graph` allows internet egress, or if authenticated `PING` fails.

## Direct checks

From the host with the debug overlay active:

```sh
./deploy/container/up.sh exec falkordb sh -c 'redis-cli --no-auth-warning ping'
```

Expected: `PONG`. Inside the orchestrator, readiness must report the graph:

```sh
./deploy/container/up.sh exec orchestrator python -c \
  "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8080/readyz').read().decode())"
```

Expected: `{"status":"ready","graph":"reachable"}`.

## Coexistence with `db/compose.yaml`

`db/compose.yaml` defines a **separate** FalkorDB instance:

- Compose project `sentinel-hunter-graphdb`.
- Published on `127.0.0.1:6379`, no password, no shared network.
- Data volume owned by that project.

The two instances do not share data and are not interchangeable. Running both
is safe only while they use different host ports; the container stack uses
`16379` when the debug overlay is active, so they do not collide.

Use the container stack when the application runs in containers. Use
`db/compose.yaml` only for isolated database work that deliberately bypasses
the application stack. Pointing both at the same graph name does not merge
them; each has its own volume.

## Not provided

- No MCP server and no REST gateway for the graph. The application uses the
  Graphiti Python client directly, per the project decision.
- No FalkorDB Browser UI. The server-only image is intentional.
- No host port in the base stack. Host access is an explicit debug opt-in.
